# Lumi plan for review (2026-11-21)

**For:** a teammate and their Claude, reviewing before the next build steps.
**Status:** routing backend built (uncommitted at time of writing). Everything else is planned or open.

Lumi is winter walking navigation for Boston (HackBoston, 36-hour build). Users report sidewalk hazards with a photo and location, AI analyzes the photo, hazards appear on a map, and routing offers three modes: **Shortest**, **Safer**, **Accessible**. See [README.md](../../README.md) for how to run it.

This document separates three things. Please keep them separate in your review:

- **Decided:** the team has chosen this. Challenge it if you see a real problem.
- **Proposed:** a suggestion from an AI review (Claude or Codex). Not agreed yet.
- **Open:** no decision yet. Your input is most useful here.

## 2. Decided

1. **Demo area:** 1.5 km radius around Marsh Plaza, BU. Extending to all of Boston comes later.
2. **Backend:** Python + FastAPI.
3. **Routing state:** the street graph is loaded once and never modified. Hazards live in a separate dict, and a per-request weight function combines the two. Reason: all routing logic stays in one place, which suits hackathon scale.
4. **Blocked segments:** all three modes skip a fully blocked segment. Shortest ignores milder hazards. If no detour exists, the API returns 404 "no route".
5. **Modes:** keep Shortest / Safer / Accessible, and explain each one to the user in the UI.
6. **Photo analysis input and runtime:** photo + location, analyzed inside FastAPI using Claude vision (Anthropic Python SDK, structured outputs).
7. **AI alone cannot mark a segment `blocked`.** What *can* is still open (see §4).
8. **Storage target:** TigerData (managed PostgreSQL). Not connected yet, and PostGIS support is unverified.

## 3. Known issues in the current code

Found by a Codex review and checked against the code. Not fixed yet.

| Severity | Issue | Where |
|---|---|---|
| High | Route lines are straight lines between intersections and ignore the stored curve geometry, so a drawn route can cut through buildings | `routing.py:104` |
| High | Converting to a simple graph keeps only the shortest of any parallel edges, so a hazard can't target the other one | `main.py:36` |
| Medium | Start and end snap to the nearest intersection (up to 250 m away). The leg to that intersection isn't in the route, and two nearby points can produce a 0 m route | `main.py:79` |
| Medium | `severity` isn't range-checked. Once AI output feeds it, a bad value could produce negative edge costs | `routing.py:53` |
| Unverified | The OSM walk network may model a street as one centerline rather than two sidewalks, so a report on one side would affect both | Check on the demo streets |
| Known | Accessible currently uses the same weights as Safer (no curb-ramp or slope data). The UI must not imply an accessibility guarantee | `routing.py:88` |

## 4. Open decisions

Review input is most valuable here.

1. **Who or what sets `blocked`?** Examples raised so far: a human reviewer, a clearly labeled demo control, several agreeing reports, or a report plus an AI that agree. The brief requires keeping confirmed reports, unverified reports, and AI predictions separate, and never calling an unverified route safe.
2. **What does the AI's output do, if it can't block?** It could raise Safer costs as an unverified hazard, appear only as a labeled prediction on the map, or something else.
3. **Model output fields.** The spike returns these candidates: `is_sidewalk_hazard`, `kind` (snow / ice / slush / puddle / obstruction / none), `severity` (minor / moderate / severe), `blocked`, `confidence`, `accessibility_issue`, `description`. Which ones to keep is not decided.
4. **Report flow.** Three options were proposed:
   - **A. Preview, then submit:** `POST /analyses` returns a draft; the user edits it; `POST /reports` saves it as unverified.
   - **B. Single request:** `POST /reports` saves the report and runs the analysis synchronously. AI failure leaves the report saved with `analysis_status=failed`.
   - **C. Async:** `POST /reports` returns at once, and a background worker analyzes the photo. Most resilient, but highest integration risk in 36 hours.
5. **Report expiry.** How a stale or wrong hazard stops affecting routes.
6. **Photo storage and retention**, upload limits, and rate limiting on report endpoints.
7. **Unparked items:** Mastra's role (MLH sponsor), domain and hosting (GoDaddy), frontend stack confirmation (tentatively Next.js + TypeScript + Tailwind + Leaflet or Mapbox).

## 5. Proposed build order

Codex proposed this order; the team hasn't agreed to it. The riskiest items come first.

1. **De-risk:** inspect the real graph on the demo streets (sidewalks vs. centerlines). Pick a demo route that has a real alternative path. Confirm the TigerData connection and Claude API credentials work.
2. **Reports:** persistence, provenance (source, time, verification status, simulated flag), expiry, mapping a report to a segment, and the agreed `blocked` rule. Test that a blockage changes all three modes.
3. **Photo analysis:** wired into the chosen flow, with an explicit failure path and the AI prediction stored separately from the report.
4. **Frontend:** mobile map, report flow, side-by-side route comparison, uncertainty labels, and a prominent Accessible limitation.
5. **Demo rehearsal:** labeled simulated hazards, plus one AI or database failure and one "no route" case. Deploy early to test phone upload, CORS, and secrets.
