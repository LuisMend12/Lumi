# Lumi plan for review (2026-11-21)

**For:** a teammate and their Claude, reviewing before the next build steps.
**Status:** routing backend, the report rules (in memory) and a first frontend map are built and committed. Report endpoints, storage and login are not built yet. Day-to-day work is tracked in GitHub issues; see [docs/team/](../team/teammate-guide.md).

Lumi is winter walking navigation for Boston (HackBoston, 36-hour build). Users report sidewalk hazards with a photo and location, AI analyzes the photo, hazards appear on a map, and routing offers three modes: **Shortest**, **Safer**, **Accessible**. See [README.md](../../README.md) for how to run it.

This document separates three things. Please keep them separate in your review:

- **Decided:** the team has chosen this. Challenge it if you see a real problem.
- **Proposed:** a suggestion from an AI review (Claude or Codex). Not agreed yet.
- **Open:** no decision yet. Your input is most useful here.

## 2. Decided

1. **Demo area:** 1.5 km radius around Marsh Plaza, BU. Extending to all of Boston comes later.
2. **Backend:** Python + FastAPI.
3. **Routing state:** the street graph is loaded once and never modified. Hazards live in a separate dict, and a per-request weight function combines the two. Reason: all routing logic stays in one place, which suits hackathon scale.
4. **Blocked segments:** all three modes skip a fully blocked segment. Shortest ignores milder hazards. If no detour exists, the API returns 404 "no route".
5. **Modes:** keep Shortest / Safer / Accessible, and explain each one to the user in the UI.
6. **Photo analysis input and runtime:** photo + location, analyzed by a Mastra agent on Google Gemini, which FastAPI calls over HTTP (see item 12). This replaced the original Claude vision plan on 2026-11-21 to avoid per-photo costs.
7. **AI alone cannot mark a segment `blocked`.** People decide, and the AI agent checks the evidence. This works like Google Maps and Waze closures: several reporters, "still there?" prompts.
8. **Storage target:** TigerData (managed PostgreSQL). Not connected yet, and PostGIS support is unverified.
9. **How a sidewalk gets blocked or cleared** (implemented in `app/reports.py`):
   - A user reports "blocked" **with a photo**. An AI agent reviews every photo. If the agent confirms, the segment is blocked right away.
   - Users **physically nearby** then get a **one-tap "Blocked or unblocked?"** prompt, with no photo and no agent.
   - The status flips when **4 different users** report the opposite of the current status.
   - A user who reports **too many blocked roads** must send photo evidence for further block reports.
10. **Login is required.** That's how "4 different people" and the abuse limit work. The login provider isn't chosen yet.
11. **Location is read only while the app is open.** A web app can't track location in the background, and continuous tracking would be a privacy liability.
12. **Decided: photo review runs as a Mastra agent on Gemini's free tier; FastAPI calls it over HTTP** (decided 2026-11-21 by both lanes). The agent lives in `mastra/` and serves `POST /review`; `make_mastra_reviewer()` in `backend/app/photo_review.py` calls it and keeps the confirm rule in Python. This replaces the earlier Claude-in-FastAPI plan, mainly to avoid per-photo API cost. Gemini's free tier may use submitted photos to improve Google's products, so demo photos must not show identifiable people. The rules still call the reviewer through one function (`PhotoReviewer`).

**Proposed by AI, accepted for step 1** (tunable values are in `app/config.py`):

| Detail | Current value |
|---|---|
| Agent rejects the photo | Report kept as **unverified**: shown on the map, labeled, doesn't affect routing |
| Agent down or erroring | Report kept as **pending** and retried; doesn't affect routing |
| Vote counting | Only votes since the last status change count; each user counts once (latest vote wins) |
| Abuse limit | 3 blocked reports within 24 h; the next one needs a photo. "Unblocked" votes are never limited |
| "Nearby" | Within 50 m of the segment (not built yet; endpoint step) |

## 3. Known issues in the current code

Found by a Codex review and checked against the code. Not fixed yet.

| Severity | Issue | Where |
|---|---|---|
| High | Route lines are straight lines between intersections and ignore the stored curve geometry, so a drawn route can cut through buildings | `routing.py:104` |
| High | Converting to a simple graph keeps only the shortest of any parallel edges, so a hazard can't target the other one | `main.py:36` |
| Medium | Start and end snap to the nearest intersection (up to 250 m away). The leg to that intersection isn't in the route, and two nearby points can produce a 0 m route | `main.py:79` |
| Medium | `severity` isn't range-checked. Once AI output feeds it, a bad value could produce negative edge costs | `routing.py:53` |
| Unverified | The OSM walk network may model a street as one centerline rather than two sidewalks, so a report on one side would affect both | Check on the demo streets |
| Known | Accessible currently uses the same weights as Safer (no curb-ramp or slope data). The UI must not imply an accessibility guarantee | `routing.py:88` |

## 4. Open decisions

Review input is most valuable here.

1. ~~**Where the photo agent runs.**~~ Decided: photo review runs as a Mastra agent on Gemini's free tier; FastAPI calls it over HTTP (decided 2026-11-21 by both lanes; see §2 item 12).
2. **Login provider:** for example Supabase Auth, Clerk, or a FastAPI-issued token. It has to provide a stable user ID.
3. **Demo with few users:** "4 different nearby users" won't happen live with one or two phones. How do we demo it honestly, for example with clearly labeled simulated users?
4. **Fixed time window for votes.** Votes currently count until the next status change, however old they are. Should old votes expire? Should a block expire if nobody answers the prompt?
5. **Milder hazards (snow, ice, slush):** how are these reported, and do unverified reports raise Safer mode's cost? Today only confirmed blocks reach routing.
6. **Model output fields.** The spike returns these candidates: `is_sidewalk_hazard`, `kind`, `severity`, `blocked`, `confidence`, `accessibility_issue`, `description`. The agent only needs a confirm / reject verdict for blocks. Which other fields to keep is open.
7. **Report flow.** Three options were proposed:
   - **A. Preview, then submit.**
   - **B. A single synchronous `POST /reports`.**
   - **C. Async worker.**
   The pending / retry design in `reports.py` fits B or C.
8. **Photo storage and retention**, upload limits, and rate limiting on report endpoints.
9. **Unparked items:** domain and hosting (GoDaddy), and frontend stack confirmation (tentatively Next.js + TypeScript + Tailwind + Leaflet or Mapbox).

## 5. Build order

Reports are being built in 4 steps:

1. ✅ **Report rules** (`app/reports.py`) with tests.
2. **Endpoints:**
   - photo upload;
   - the one-tap vote;
   - map a report's location to the nearest segment;
   - the "nearby" check;
   - wire in the real photo agent.
3. **Storage:** TigerData, with provenance (source, time, verification status, simulated flag).
4. **Login.**

Codex proposed the overall order below; the team hasn't agreed to it. The riskiest items come first.

1. **De-risk:** inspect the real graph on the demo streets (sidewalks vs. centerlines). Pick a demo route that has a real alternative path. Confirm the TigerData connection and Claude API credentials work.
2. **Reports:** the 4 steps above. Test that a blockage changes all three modes (done for the rules).
3. **Photo analysis:** wired into the chosen flow, with an explicit failure path and the AI prediction stored separately from the report.
4. **Frontend:** mobile map, report flow, side-by-side route comparison, uncertainty labels, and a prominent Accessible limitation.
5. **Demo rehearsal:** labeled simulated hazards, plus one AI or database failure and one "no route" case. Deploy early to test phone upload, CORS, and secrets.
